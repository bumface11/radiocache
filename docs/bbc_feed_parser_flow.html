Explain BBC feed parser data scenarios with HTML flow diagrams

This page summarizes the data-handling logic in radio_cache/bbc_feed_parser.py on main. It focuses on how category scans, fallback tags, backfill, and programme parsing interact to produce a deduplicated output list.

Scope note: this is an implementation guide for current behavior, not a formal architecture spec.

Glossary

PID: BBC identifier used for episode/brand/series rows (episode PID is derived from URN tail for playable items).
Brand: Top-level programme container (e.g. show-level parent).
Series: Sub-container under a brand. Can be a true BBC series PID, or a synthetic key in playable-listing cases.
Slug: Category key used with playable API (e.g. drama, thriller).
Container backfill: Optional second pass that fetches all episodes for discovered brand/series containers.
Inherited categories: Category tags gathered during slug scans and applied to episodes found during container backfill.

1) Basic category listing ingestion

For each slug, the parser pages through playable listing items, parses each item, channel-filters it, then stores/merges by episode PID.

2) Slug/category fallback when item categories are empty

If playable item categories is empty/missing, the parser still tags the programme with the slug display name used to discover it.

slug=thrilleritem.categories=[]stored categories include “Thriller”

3) Category merging across multiple slug scans

When the same episode PID appears in multiple slugs, category sets are merged instead of overwritten.

Example: PID m000abcd found in drama and later thriller → merged set includes both Drama and Thriller.

4) Container backfill + inherited categories

With backfill_containers=True, the parser expands discovered series_pid / brand_pid containers to capture older episodes. This is important when category pages only expose recent episodes for large brands/containers.

Synthetic IDs containing :: are excluded from container backfill (not valid BBC container PIDs).

Concrete case: a very large brand/container where category paging sees only recent episodes; container backfill pulls older catalogue episodes and applies inherited tags from the discovery pass.

5) Priority brand backfill (without container backfill)

If priority_brands is provided while backfill_containers=False, the parser runs a smaller brand-focused backfill (up to 5 pages each) to pull fresh episodes for active brands.

6) _parse_programme_item() brand/series derivation paths

6a) Ancestor-rich detail payloads

When two or more ancestors are present, ancestor[0] and ancestor[1] are used as real brand/series IDs and titles, and episode title prefers tertiary/entity title.

6b) Playable listing with synthetic series derivation

If container type is brand and there is secondary + tertiary/entity title, the parser derives synthetic series key brand_pid::secondary_title (unless one of the exceptions below applies).

6c) Collapse of known synthetic-series brands

Known brands (currently The Archers + Omnibus IDs) collapse to a canonical brand-level series rather than per-headline synthetic series rows.

6d) Date-like secondary titles do not become series

Secondary labels matching DD/MM/YYYY are treated as date labels, not real series; series fields are left empty in that branch.

Extra guard: if row is synthetic brand::series and episode title equals series title, it is canonicalized back to one brand-level series.

7) Final deduplication and merged category output

Final output iterates one programme per PID and replaces its category string with the fully merged category set, sorted alphabetically for deterministic results.

Result: one row per PID with categories merged from all discovery paths.
